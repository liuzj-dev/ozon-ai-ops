# ozon-ai-ops

> AI-powered automation toolkit for Ozon cross-border e-commerce operations

把 Ozon 跨境店铺的日常运营流程，用 LLM 和确定性计算自动化掉。面向真实铺货场景，不是 demo。

---

## 1. 问题

做 Ozon 俄罗斯市场，运营每天要花大量时间在三件重复劳动上：

- **写不了俄语文案** —— 中文翻译成俄语后不符合当地人阅读习惯，转化率低
- **店铺问题靠肉眼排查** —— 几十上百个商品，哪个该先修、修什么，全靠经验
- **算不清真实利润** —— 平台佣金、代理佣金、跨境物流、提现手续费、退货费层层扣减，手工算容易出错

三个模块分别对应这三个问题，形成闭环：**生成 → 诊断 → 定价**。

## 2. 方案

| 模块 | 输入 | 输出 | 技术 | 状态 |
|---|---|---|---|---|
| **A. Listing 生成** | 中文商品参数表 | 俄语标题 / 卖点 / 描述 / 关键词 | LLM | ✅ |
| **B. 商品 AI 诊断** | 商品明细（标题、售价、内容分、价格指数） | 标题诊断 + 优化后标题 + 内容补齐清单 + 定价建议 + 优先级 | LLM | ✅ |
| **C. 定价核算** | 成本、重量、佣金率 | 建议售价 + 六项成本拆解 + 净利润 + 双利润率 | 确定性计算 | ✅ |

## 3. 效果

### 模块 A：俄语 Listing 生成

| 指标 | 手工 | 本工具 | 提升 |
|---|---|---|---|
| 单 SKU 文案耗时 | 约 25 分钟 * | **2.5 秒** | **约 600x** |
| 100 SKU 批量生成 | 约 42 小时 | **约 4 分钟** | **约 600x** |

\* 手工口径：中文撰写 + 机器翻译 + 俄语校对。不掌握俄语的运营者实际无法独立完成这条链路。

### 模块 B：商品 AI 诊断

对 **49 个真实在售商品** 全量诊断：

```
Token：输入 31,447 / 输出 16,101      成本约 0.3 元
分档：P0 7 个 / P1 22 个 / P2 20 个
```

**诊断质量样例**（真实抓出的问题）：

|---|---|
| 混入中文标点 | `...нескользящий, розовый。Товары для спорта` |

## 4. 技术

| 组件 | 选型 | 为什么 |
|---|---|---|
| LLM | DeepSeek API | 中文理解好、价格低、OpenAI 兼容 |
| 数据处理 | pandas | —— |
| 输出 | openpyxl | 直接产出可交付的 Excel |
| 配置 | python-dotenv | Key 与代码分离，避免泄露 |

### 关键设计决策

**① 结构化输出**
用 JSON mode 强制模型返回固定字段，避免解析自由文本。字段缺失或类型异常时做归一化兜底，不让脏数据污染输出。

**② 失败不中断**
单条失败重试 3 次后跳过，整批继续跑完，导出结果带 `status` 列标明每条的成功/失败。

**③ 错误路径优化：18.1s → 1.1s**
最初 LLM 客户端写在重试循环内部，导致「缺少 API Key」这类**不可重试的配置错误**也被当成网络抖动重试 3 次。
将客户端移到循环外创建后，配置错误立刻抛出。**关键是区分「可重试错误」与「不可重试错误」。**

**④ 配置校验按格式识别，而非匹配固定字符串**
`.env.example` 的占位符文案从 `sk-xxxx` 改成 `sk-你的apikey` 后，
原先只判断 `startswith("sk-xxx")` 的校验会**误判为有效 Key**，直到调 API 才报出难懂的鉴权错误。
改为多规则识别（关键字标记 + 长度 + ASCII 校验），覆盖 5 种占位符场景。

**⑤ 优先级分档：从模型判定改为相对排名**（本模块最有价值的一次迭代）

| 版本 | 做法 | 结果 | 问题 |
|---|---|---|---|
| v1 | 模型直接输出 P0/P1/P2 | P0 45/49（92%） | 几乎全是 P0，失去排序意义 |
| v2 | 收紧提示词判定标准 | P0 3 / P1 46 / P2 0 | 挤在 P1，区分度仍不足 |
| **v3** | **模型只打 0-100 严重度分，分档由代码按批次内相对排名完成** | **P0 7 / P1 22 / P2 20** | ✅ 分布合理 |

根因：**LLM 给出的绝对分值会被压缩在窄区间**（实测全部落在 42-78），固定阈值无法稳定分档。
改用相对排名后，既不受模型打分尺度漂移影响，又直接回答了运营真正关心的问题——**「这批商品我该先修哪几个」**。
阈值以比例配置在 `product_intel.py` 的 `P0_RATIO` / `P1_RATIO`，调整无需重跑模型。

**⑥ 确定性计算与 LLM 分离**
定价核算是纯数学，**不需要也不应该用 LLM**。模块 C 完全本地计算：
零 token 成本、结果可复现、毫秒级返回。把 LLM 用在真正需要判断力的地方（文案生成、问题诊断），
把确定性任务留给代码——这是 AI 应用的基本功。

**⑦ 网页工具 → Python 引擎的移植验证**
模块 C 的业务逻辑来自作者自研的网页版定价工具（v1→v7）。
移植后做了**交叉验证**：用 Node 执行原版 JS 生成 60 条参考结果，
与 Python 版逐条比对物流费、代理佣金、净利润三个关键值。

```
共 60 条，不一致 0 条
结论：完全一致 ✅ 移植无偏差
```

移植过程的三点改进：
1. **费率表外置为 `data/rates.json`** —— 物流商调价时改配置即可，不必改代码（原版硬编码在 HTML 里）
2. **取消全局状态** —— 物流商 / 配送方式作为显式参数传入，可并发、可测试
3. **反推定价增加收敛检测** —— 目标利润率不可达时明确标出，而不是静默返回错误价格

## 5. 快速开始

```bash
# 1. 安装依赖
pip install -r requirements.txt

# 2. 配置 API Key（模块 C 不需要 Key，纯本地计算）
copy .env.example .env        # Windows
# 然后编辑 .env，填入你的 DEEPSEEK_API_KEY

# 3. 运行
python main.py listing                        # 模块 A：生成俄语 Listing
python main.py diagnose                       # 模块 B：诊断商品
python main.py price                          # 模块 C：定价核算
python main.py diagnose --limit 5             # 只跑前 5 条（低成本试跑）

# 模块 C 可指定物流方案与目标利润率
python main.py price --logistics POST --margin 0.30
python main.py price --logistics CEL --delivery Express --margin 0.20
```

输出文件在 `data/output/`。

```
├── .env.example         Key 配置模板
└── requirements.txt
```
